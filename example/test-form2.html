pdftoformext — manual test form 2

The fixture for this page is example/test-form2.pdf: a six-page, text-only SAP-style material master report with no AcroForm at all, so every one of its ~930 keys comes out of the geometric pass under table.*. Nothing on this page hints at which key belongs where — ids are framework-generated noise, names are control paths, several inputs have neither, and two ids are duplicated. Every mapping has to be made by clicking the field and reading the key's value in the dropdown, which is the workflow this harness exists to exercise.

Expected keys are in HTML comments beside each field so a run can be checked; the extension never reads them. Keys marked ⚠ are ones whose name lies about their contents — a side effect of a two-pair "label value label value" row being read as a five-column table — and they are the most valuable ones to map, because nothing but the visible value identifies them.

Run context

Values here live in the page header and the “Selection Criteria” block of page 1. The header is a four-row block whose cells land in scattered columns, so the keys are positional.

Material master — basic data

Page 2, material 100000-A012. Its “Basic Data” block is two label/value pairs per line, which the extractor reads as a five-column table — so the header-derived keys carry the first data row's text, not a heading. table.7.pc.2 holds the net weight.

Source of supply — primary

Page 2, first purchasing row. Expect #wd0003-src input[name="ctl00$cph$vendor"], not input[name="ctl00$cph$vendor"].

Source of supply — alternate

Page 2, second purchasing row. Same six names as the form on the left; only the form scope tells them apart.

Stock by plant

Page 6, the MB52 grid — 20 data rows across sixteen column bands. Rows are not column-consistent: right-aligned quantities drift between bands, so row 4's on-hand figure is c6 where rows 1–3 use c5. Selectors here look like #wd0005-grid > tbody > tr:nth-of-type(1) > td:nth-of-type(3) > input. On-hand is a text input on purpose: "48,200" through toNumber reads the comma as a decimal point and yields 48.2, so a number input would quietly be wrong.
